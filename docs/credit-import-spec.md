# ייבוא אשראי, סיווג לומד ויועץ

אפיון לפיצ׳ר השני הגדול של BudgetTracker. המסמך הזה הוא מקור האמת,
והקוד אמור להתיישב איתו. אם משהו כאן מתברר כלא נכון, מתקנים כאן קודם.

## ההחלטות שננעלו

| נושא | ההחלטה |
|---|---|
| היחס לתקציב | שכבה נפרדת. העסקאות לא נכנסות למסך התכנון אלא מוצגות מולו |
| כרטיסים | של שניכם, וכל מה שמיובא גלוי לשני חברי התקציב |
| חברות | מקס וכאל בלבד בשלב הראשון |
| יועץ | שלב שני, מעל נתונים שכבר עובדים, דרך Vercel Function |
| יומן | מחוץ לגרסה הזו |

## מה לא נבנה, ולמה

**אין גרידה של אתר האשראי ואין שמירת פרטי התחברות.** הייצוא הידני נותן
בדיוק את אותו מידע, בלי להחזיק סיסמאות של חשבון פיננסי בתוך אפליקציה
פרטית. זה לא סעיף שנפתח מחדש בהמשך.

**אין ייעוץ השקעות.** היועץ עונה על שאלות תזרים מהמספרים שלכם, למשל
"כמה נזיל יש לי לטיול", ולא על מה לעשות בכסף.

**העסקאות לא הופכות לשורות אוטומטית.** המסך החודשי הוא הסכמה בין שני
אנשים על מה מתוכנן. מספר שנכנס לבד הוא לא מספר שהסכמתם עליו.

## למה שכבה נפרדת

זו ההחלטה שמכתיבה את כל השאר, ולכן כדאי שתהיה כתובה.

היום רשומה בתקציב היא דבר שמישהו טרח להזין, ולכן הסכים לו. אם 200 שורות
אשראי ייכנסו לאותו מקום, מסך התכנון ייעלם מתחת ליומן עסקאות, והערך
המרכזי של האפליקציה, שני אנשים שמסתכלים על אותה תמונה מוסכמת, יישחק.

לכן העסקאות חיות באוסף משלהן, ומסך חדש מציג את שתי התמונות זו מול זו.
מי שרוצה יכול לקדם עסקה בודדת לשורה בתקציב, אבל זו פעולה יזומה.

## מודל הנתונים

### `transactions/{txId}`

אוסף ברמה העליונה, כמו `entries`, כדי שיישמר אותו דפוס של שאילתה לפי
`budgetId` ו-`month` ואותו דפוס כללי אבטחה.

```
budgetId         string          תקציב הבית שאליו הייבוא שייך
month            'YYYY-MM'       נגזר מתאריך הרכישה
date             'YYYY-MM-DD'    תאריך הרכישה
merchant         string          שם בית העסק כפי שהופיע בקובץ
merchantKey      string          הצורה המנורמלת, לפיה מתבצעת ההתאמה
amount           number          בשקלים. שלילי בזיכוי
originalAmount   number?         בעסקה במט״ח
originalCurrency string?         'USD' וכדומה
issuer           'max' | 'cal'
cardLast4        string
installment      { n, of }?      כשהקובץ מציין תשלום n מתוך m
category         string | null   קטגוריה בתקציב, או null כשלא סווג
categorySource   'rule' | 'manual' | null
groupKey         string?         אותו קיבוץ שכבר קיים בשורות
cardOwnerUid     string          של מי הכרטיס
importedBy       string          מי ביצע את הייבוא
importId         string          מזהה האצווה, לביטול ייבוא שלם
entryId          string?         כשקודמה לשורה בתקציב
```

### `budgets/{budgetId}/merchantRules/{ruleId}`

```
pattern      string    מחרוזת מנורמלת להתאמה
category     string
groupKey     string?
hits         number    כמה פעמים נוצלה, לדירוג התאמות
createdBy    string
updatedAt    timestamp
```

### `budgets/{budgetId}/imports/{importId}`

רשומת ביקורת לכל ייבוא: מי, מתי, איזו חברה, כמה שורות נקראו, כמה נכתבו,
כמה דולגו כפילויות. בלי זה אי אפשר לבטל ייבוא שגוי ואי אפשר להסביר
למשתמש מספר שלא מסתדר לו.

## אידמפוטנטיות, החלק שהכי קל לפשל בו

אדם יכול לייבא את אותו קובץ פעמיים, או לייבא קובץ של 1 עד 15 בספטמבר
ואחר כך קובץ של כל ספטמבר. אם הכתיבה לא אידמפוטנטית, הסכומים מוכפלים
והאפליקציה משקרת. זה אותו שיקול שהוביל למזהים הקבועים של החיובים
הקבועים ושל שורות הטיול.

**מזהה המסמך נגזר מתוכן העסקה ולא אקראי:**

```
txId = hash(issuer | cardLast4 | date | amount | merchantKey) + '_' + occurrence
```

`occurrence` הוא האינדקס של העסקה בתוך קבוצת עסקאות זהות לחלוטין
**באותו יום**. שתי כוסות קפה באותו בית קפה באותו יום הן שתי עסקאות
אמיתיות, ולכן הן חייבות לקבל מזהים שונים, אבל ייבוא חוזר של אותו קובץ
חייב למפות אותן לאותם שני מזהים.

זה עובד כי התאריך כבר חלק מהמפתח: כפילויות יכולות להתנגש רק בתוך יום
אחד, וסדר המנייה בתוך יום יציב בין קבצים חופפים. כתיבה נעשית ב-`setDoc`
עם המזהה הזה, כך שייבוא חוזר דורס את אותה רשומה במקום ליצור חדשה.

**מה שנשמר בייבוא חוזר:** `category`, `categorySource`, `groupKey`
ו-`entryId`. סיווג ידני שמישהו עשה לא נמחק בגלל ייבוא נוסף.

## תאריך רכישה מול תאריך חיוב

קובץ האשראי מכיל את שניהם. הבחירה כאן משנה לאיזה חודש הכסף שייך.

**הכרעה: תאריך הרכישה.** זה מה שאדם זוכר וזה מה שמתיישב עם מסך התכנון,
שהוא חודשי ולא לפי מועד חיוב הבנק. תאריך החיוב נשמר בכל זאת, כי הוא
הנכון לשאלת תזרים מזומנים, והיועץ בשלב ד יצטרך אותו.

**תשלומים:** כל תשלום הוא עסקה בפני עצמה בתאריך החיוב שלו, מתויגת
`installment`. כך קניה ב-12 תשלומים מופיעה כ-12 חיובים קטנים לאורך
השנה, וזו התמונה הנכונה לתקציב חודשי.

**מט״ח:** הסכום השקלי הוא `amount`, כי הוא מה שירד בפועל. המקורי נשמר
לתצוגה בלבד.

**זיכויים:** סכום שלילי, מותר ב-`transactions`. שימו לב שכללי `entries`
דורשים `actualAmount >= 0`, ולכן **זיכוי אינו ניתן לקידום לשורה
בתקציב**. הוא מקטין את הסכום בקטגוריה במסך ההשוואה, וזה מספיק.

## סיווג לומד

בלי קסמים ובלי מודל שמנחש. טבלת כללים שנבנית מהתיקונים שלכם.

1. **נרמול** שם בית העסק: הסרת פיסוק, מספרי סניף, ספרות בודדות ורווחים
   כפולים. `שופרסל דיל 443` ו-`שופרסל דיל  ראשל״צ` מתכנסים לאותו מפתח.
2. **התאמה**: הכלל הארוך ביותר שמתאים מנצח, כדי ש-`רמי לוי שיווק` יגבר
   על `רמי`.
3. **למידה**: כשמסווגים שורה במסך האישור, מוצעת תיבה "תמיד ככה עבור
   *שם העסק*". סימון שלה כותב כלל.
4. **זרע התחלתי**: רשימה קצרה של רשתות מוכרות, שמסומנת בבירור כניתנת
   לעריכה. היא חוסכת את החודש הראשון, לא מחליפה את הלמידה.

אחרי חודשיים רוב השורות אמורות להסתווג לבד. זה גם צפוי וגם בר תיקון,
בניגוד למודל שמנחש ואי אפשר להתווכח איתו.

## המסכים

### ייבוא

בחירת חברה, בחירת קובץ, ואז מסך אישור. הקריאה מתבצעת בדפדפן, שום קובץ
לא נשלח לשרת.

**תלות חדשה:** `xlsx` לקריאת הקובץ. זו הספרייה הכבדה הראשונה בפרויקט,
שיש בו היום שלוש תלויות בלבד. לכן היא נטענת ב-`import()` דינמי רק בכניסה
למסך הייבוא, ולא נכנסת לחבילה הראשית.

### אישור

טבלה של מה שנקרא: תאריך, בית עסק, סכום, וכפתור קטגוריה. שורות שלא
סווגו עולות למעלה, כי הן מה שדורש ממך משהו. אפשר לבחור כמה שורות ולסווג
יחד. למעלה שורת סיכום: כמה נקראו, כמה כבר קיימות ויידלגו, וכמה ייכתבו.

הכתיבה באצוות של 500, המגבלה של Firestore.

### תכנון מול מציאות

לחודש הנבחר, לכל קטגוריה: כמה תוכנן, כמה יצא בפועל בכרטיס, והפער. מתחת
לזה שתי תצוגות שעונות על "מתי אני מוציא הרבה ועל מה":

- בתי העסק הגדולים של החודש, מדורגים
- התפלגות לפי שבוע בחודש

הגרפים בכתב יד כמו גרף ההיסטוריה הקיים. אין ספריית גרפים בפרויקט ואין
סיבה להכניס אחת.

## כללי אבטחה

`transactions` מקבל בדיוק את דפוס `entries`: קריאה וכתיבה רק לחברי
התקציב, עם ולידציה על הטיפוסים ועל התאמת `date` ל-`month`. `cardOwnerUid`
לא ניתן לשינוי אחרי היצירה.

`merchantRules` ו-`imports` הם תתי אוספים של התקציב, ולכן נשענים על
`isMember` הקיים.

## שלב ד: היועץ

`api/advisor.js` כפונקציה ב-Vercel.

1. הלקוח שולח את השאלה ואת ה-ID token של Firebase.
2. **השרת מאמת את הטוקן** ובודק חברות בתקציב בעצמו. בלי זה כל אדם
   ברשת יכול לשרוף את המפתח שלך ולקרוא נתונים של אחרים.
3. השרת מרכיב הקשר **מצרפי**: יעדים לחודש, מה יצא עד עכשיו לפי קטגוריה,
   קצב מול שלושת החודשים הקודמים, חיובים קבועים ידועים קדימה, תשלומים
   פתוחים, ויתרות של מטרות חיסכון. לא רשימת בתי עסק גולמית. זה גם זול
   יותר וגם מכבד יותר.
4. תשובה, עם מגבלת קצב יומית לכל משתמש.

**מגבלה שכדאי לומר מראש:** יש לזה עלות לפי שימוש, ומפתח API שצריך לחיות
במשתני הסביבה של Vercel ולא ב-git.

## מה חוסם עכשיו

**אני צריך קובץ ייצוא אמיתי אחד ממקס ואחד מכאל.** אי אפשר לכתוב מפענח
לקובץ שלא ראיתי: כל חברה מייצאת עמודות בשמות אחרים, לפעמים עם שורות
כותרת מיותרות מעל, ולפעמים עם תאריך בפורמט שונה. ניחוש כאן מתגלה רק
כשהמספרים יוצאים לא נכון.

אפשר עם סכומים אמיתיים, ואפשר אחרי שתחליף שמות ומספרים אם נוח לך יותר.
מה שחשוב הוא המבנה: אותן עמודות, אותה כותרת, אותו פורמט תאריך.
